# PoseSync Studio 技術概要

各機能について、**採用した仕組み / 意識したこと / 他の選択肢 / 今後の展望** を簡単にまとめる。
詳しい経緯は [design_changes.md](design_changes.md)、動かし方は [how_to_run.md](how_to_run.md)、検証結果は [user_test.md](user_test.md)。

---

## 0. 全体構成

| | 内容 |
|---|---|
| 仕組み | Unity(UI・体験フロー・タレント表示・合成)と、ローカルの Python サーバー(姿勢推定・ポーズ判定・切り抜き)の2つに分け、HTTP でやり取りする。 |
| 意識したこと | 推論は Python の方がライブラリが揃っていて試行錯誤が速い。一方、表示と体験は Unity にまとめる。判定・切り抜きは `IPoseEstimator` / `ISegmenter` というインターフェースの裏に隠し、実装を差し替えられるようにした。 |
| 他の選択肢 | Unity 内で推論する(Sentis / Barracuda + ONNX モデル)。配布は1本で済むが、モデルの変換や前後処理の実装に時間がかかるため、1週間の制作期間では見送った。 |
| 今後 | インターフェースはそのままに、Unity 内推論の実装を追加すれば、サーバー無しの単体アプリにできる。 |

## 1. 体験フロー(状態遷移)

| | 内容 |
|---|---|
| 仕組み | `BoothFlow` が「待機 → 立ち位置 → ポーズを考える → カウントダウン → 判定・合成 → 結果」を、Unity 6 の `Awaitable`(async/await)で上から順に書いた1本の流れとして管理する。「もう一度」は立ち位置から、「終了する」はあいさつの後で待機画面へ戻る。Esc で終了。 |
| 意識したこと | 体験の順序がコードを読むだけで分かること。状態が変わるたびにイベントを出し、ログ記録などの別機能が流れの本体を書き換えずに追加できるようにした。 |
| 他の選択肢 | Animator のステートマシンや、状態ごとのクラスに分ける State パターン。状態が多く分岐が複雑になればそちらの方が見通しが良い。 |
| 今後 | 会場運用向けに、無操作が続いたら待機画面へ戻るタイムアウトや、管理者用の設定画面を追加する。 |

## 2. 立ち位置の自動判定

| | 内容 |
|---|---|
| 仕組み | 立ち位置ガイド中は約 0.15 秒ごとに小さな画像を Python の `/detect` に送り、**両肩・両肘**が枠の中かつ枠の高さの 40〜90% にあるかを見る。その状態が 2.5 秒続いたら自動で撮影へ進む。判定できない時(サーバー未起動など)は「撮影開始！」ボタンに切り替える。 |
| 意識したこと | ユーザーテストで、立ち位置に最大 51 秒かかった回があった。ボタンを押させずに進めることで迷う時間を減らした。**頭は髪型やフード、帽子で検出が不安定**なので、判定には腕を使った。 |
| 他の選択肢 | 顔検出で判定する / 人物の切り抜き面積で判定する / ボタンのみにする。 |
| 今後 | 「もう少し下がって」のように、ずれている方向をボイスで案内する。 |

## 3. タレントのポーズ制御

| | 内容 |
|---|---|
| 仕組み | ポーズは AnimationClip ではなく、**画面座標での上腕・前腕の向き(方向ベクトル)**と、指の形・手首の向き・体と首の傾き・表情を `poses.json` に書いて定義する。`TalentRig` が Humanoid の骨をその向きに回し、ポーズ間はなめらかに補間する。 |
| 意識したこと | **撮影者の動きをコピーしない**(事前に決めたポーズだけを取る)ので、ポーズ破綻やめり込み、不適切な動きが原理的に起きない。同じ JSON から Python 側の判定テンプレートも作るので、見た目と判定がずれない。Humanoid 共通の仕組みなので、モデルを替えても定義はそのまま使える。 |
| 他の選択肢 | 撮影者の動きにリアルタイムで追従させる(企画段階で不採用。ブランドを損なうリスクとポーズ破綻のため)。モーションキャプチャや手付けのアニメーションクリップを使う。 |
| 今後 | ポーズの種類を増やす。プレビュー画像を見ながら値を調整できる簡単なエディタ画面を作る。 |

## 4. ポーズ判定

| | 内容 |
|---|---|
| 仕組み | MediaPipe Pose で関節を推定し、上半身(肩・肘・手首)だけから特徴量を作る。特徴量は、腕4本の向き、肩幅で正規化した手首の位置、肩の傾き。テンプレートとの距離は「度」に揃えた重み付き RMS で測り、一番近いポーズを選ぶ。距離が 40 を超える、または両肩が見えていない時は「おまかせ」にする。シャッター前後の5フレームを判定し、多数決でまとめる。 |
| 意識したこと | 足先まで映すには2m以上離れる必要があったため、**上半身だけ**で判定する。体の前を横切る腕は推定の信頼度が極端に下がるが、位置自体はおおむね正しかった。そこで信頼度による打ち切りは両肩だけにした(ハートの正解率が改善)。ハートは「どちらの手か」ではなく、**画面のどちら側(タレント側)に作ったか**で定義した。 |
| 他の選択肢 | 骨格を入力にした小さな分類モデル(MLP など)を学習させる / 手の検出(MediaPipe Hands)で指の形まで判定する。 |
| 今後 | ユーザーテストの骨格データを貯めて、テンプレートを実測の平均に置き換える、または学習モデルに移行する。指の形(ピースかどうか)まで見るようにする。 |
| 結果 | 自分のサンプルで正解率 87%。3名・16回のユーザーテストで、意図したポーズが選ばれた割合は 92%。 |

## 5. Unity と Python の通信

| | 内容 |
|---|---|
| 仕組み | FastAPI のローカル HTTP サーバー(`/judge` `/cutout` `/detect` `/health`)。Unity は `UnityWebRequest` で JPEG を送る。サーバーに繋がらない時は、開発用のデバッグ判定に自動で切り替える。体験中に応答が無い時は「おまかせ」にして、体験を止めない。 |
| 意識したこと | 判定は撮影時の1往復だけなので、常時接続は不要。HTTP にしたことで、ブラウザやコマンドからも単体で試せ、テストも書きやすくなった。 |
| 他の選択肢 | UDP / WebSocket(企画書の案)。プレビュー中に常時判定する場合はこちらの方が向く。 |
| 今後 | 判定と切り抜きを1回の通信にまとめて、待ち時間をさらに短くする。 |

## 6. 撮影者の切り抜き

| | 内容 |
|---|---|
| 仕組み | 姿勢推定と同じ MediaPipe Pose の人物マスクを使い、元画像を手がかりにしたガイデッドフィルタで輪郭を整える。抜けやすい部分は関節の位置で補う(腰→膝→足首に沿った帯を足す、手の周りは採用する基準をゆるめる)。追加モデル(DeepLab / selfie multiclass)を重ねる方式も選べ、`cutout_compare.py` で比較できる。 |
| 意識したこと | ユーザーテストで、暗いズボンの膝から下や、ハートの親指が抜けた。姿勢推定の結果を使えば、追加の推論コストほぼ無しで補える。一度、マスクの形の違い(H,W,1)が原因で約 4.7GB の配列ができ、タイムアウトする不具合を出したため、2D に揃える処理とテストを入れた。 |
| 他の選択肢 | 髪の毛まで綺麗に抜ける専用モデル(MODNet、RobustVideoMatting など)。品質は高いが重く、導入にも時間がかかる。グリーンバック。 |
| 今後 | 専用の切り抜きモデルを試し、グッズ(うちわ・ペンライト)も人物として残せるようにする。 |

## 7. 合成と結果写真

| | 内容 |
|---|---|
| 仕組み | `PhotoCompositor` が 1080×1080 に「背景 → 撮影者の影 → 撮影者 → タレント」の順で重ねる。タレントは**画面に表示していた位置と大きさのまま**重ねる。結果は PC 内に保存し、元の写真も別に残す(切り抜きの調整用)。 |
| 意識したこと | 撮影中に画面で見ていた構図が、そのまま写真になること。撮影者には、カメラ映像と同じ明るさ補正をかけて揃えた。 |
| 他の選択肢 | 画面全体をスクリーンショットする(UI まで写り込む)/ Python 側で合成する。 |
| 今後 | 背景やフレームを選べるようにする。QR コードで写真をスマホに渡す。 |

## 8. シャッター演出

| | 内容 |
|---|---|
| 仕組み | 透明なしのシャッター動画を、中央 1:1 に切り出し、黒を透明にした連番 PNG に変換した(`convert_shutter.py`)。撮影の瞬間に「閉じる」を再生して**閉じきったコマで止め**、判定・切り抜き・合成が終わったら「開く」を再生する。 |
| 意識したこと | 処理の待ち時間(約 0.4〜0.7 秒)を演出で隠す。閉じている時間は毎回変わるので、閉じると開くを別の連番にした。写真はカメラ映像から直接取るので、シャッターは写り込まない。シャッターの裏ではタレントの遷移アニメを省き、待ち時間を短くした。 |
| 他の選択肢 | 動画のまま VideoPlayer で再生する(透明付き WebM)/ UI で羽根を描く / 白フラッシュ(素材が無い時はこれになる)。 |
| 今後 | 撮影モードに合わせて演出の種類を選べるようにする。 |

## 9. ガイド音声・BGM

| | 内容 |
|---|---|
| 仕組み | `VoicePlayer` がボイスを順番待ちにし、1つずつ流す。前のボイスが終わるまで次を流さず、間は必ず 0.5 秒以上空ける。カウントダウンだけは例外で、正確に1秒ごとに流す。`BgmPlayer` が BGM をループ再生し、ボイスの間は音量を下げる。 |
| 意識したこと | 立ち位置に早く入るなど、操作の速さによってボイスが重なり、聞き取れなくなるのを防ぐ。画面の文字は残し、音が出せない会場でも使えるようにした。再生中かどうかはクリップの長さで管理し、音の出ない自動テストでも同じ時間で進むようにした。 |
| 他の選択肢 | 新しいボイスが前のボイスを打ち切る方式(重ならないが、案内が途中で切れる)。 |
| 今後 | 判定結果に応じたひとこと(「ハートがつながったね」など)を加える。タレント本人の声に差し替える。 |

## 10. タレントの切り替え

| | 内容 |
|---|---|
| 仕組み | `TalentSwitcher` がタレントの一覧(表示名とモデル)を持つ。右下のアイコンを押すと名前が上方向に開き(ドロップアップ)、選んだモデルだけを有効にする。切り替え時に、体験フローとカメラの構図を新しいモデルに付け替える。シーン生成時に VRM をすべて並べ、表示名は VRM ファイル内のモデル名を使う。 |
| 意識したこと | タレントを増やす時にコードを書かなくて済むこと(VRM を置いて再生成するか、一覧に1行足すだけ)。撮影中に別人へ入れ替わらないよう、操作できるのはスタート画面だけにした。構図はモデルの体格から作り直すので、背丈が違っても頭の位置が揃う。 |
| 他の選択肢 | 必要な時にモデルを読み込む(Addressables や実行時の VRM 読み込み)。人数が多い時はメモリの点で有利。 |
| 今後 | タレントごとにポーズやボイスを変えられるようにする。モデルを実行時に読み込み、ビルドし直さずに追加できるようにする。 |

## 11. 見た目の調整と確認用ツール

| | 内容 |
|---|---|
| 仕組み | 明るさ・タレントの位置と大きさ・枠などの調整値を `BoothLook` にまとめ、Play 中に動かすとその場で反映されるようにした。シーンはエディタ拡張(`BoothSceneBuilder`)でコードから生成し、Play しなくても確認できるプレビュー画像の出力ツールや、体験を自動で進めるテスト(`FlowProbe`)を用意した。 |
| 意識したこと | 見た目の細かい調整を何度も繰り返すので、数値を変えてすぐ確かめられること。シーンを手で組まず再生成できるようにし、設定の食い違いを減らした。自動テストで「見本と撮影時のポーズ位置が同じか」「ボイスの間隔が守られているか」を数値で確認した。 |
| 他の選択肢 | シーンを手作業で組み、Prefab で管理する。 |
| 今後 | 調整値をファイルに保存して、会場ごとに切り替えられるようにする。 |

## 12. 検証(ユーザーテスト)の仕組み

| | 内容 |
|---|---|
| 仕組み | Unity が体験ごとに、各ステップの所要時間・途中でやめた場所・判定結果・切り抜きの成否を記録する。記録係が結果画面で数字キーを押し、参加者の「とったつもりのポーズ」を残す。Python は判定に使った骨格を残すので、閾値を変えても撮り直さずに再計算できる。集計ツールが正解率と混同行列、迷った箇所を表にまとめる。 |
| 意識したこと | 企画書・ES に**数字で載せられる**形で残すこと。画像は保存せず骨格だけを残し、個人データを最小限にした。 |
| 他の選択肢 | アンケートのみ / 画面録画を見返して手で数える。 |
| 結果 | 意図したポーズが選ばれた割合 92%、撮影まで完了 94%、判定の待ち時間 中央値 0.69 秒。立ち位置で迷う回があったことが、自動開始の導入につながった。 |
| 今後 | 参加者を増やし、グッズを持った場合や、子ども・背の高い人などの条件別に正解率を出す。 |

## 13. 素材と個人データの扱い

| | 内容 |
|---|---|
| 仕組み | 再配布禁止の素材(モデル・シャッター・ボイス・効果音・BGM・アイコン・人型)はすべて `Assets/ThirdParty/` と `素材/` に置き、GitHub には上げない。撮影写真・ログ(どの階層の `data/` も)も除外した。素材が無い環境でも動くよう、それぞれに代わりの動作(マネキン・白フラッシュ・無音など)を用意した。 |
| 意識したこと | 公開リポジトリでも、規約違反と個人データの流出が起きないこと。push の前に毎回、対象ファイルを確認した。 |
| 今後 | 素材の置き場所と取得方法を README にまとめてあるので、それに沿って環境を再現できるようにする。 |
